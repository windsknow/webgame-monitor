# 部署与迁移

2026-11-12 的决定：先把采集部署起来，内容存下来之后再定怎么筛选。现在线上每天只跑 `python3 run.py crawl`，不合并、不入库、不出网页。

部署方式和 taptap-spider 一样：**采集在 GitHub Actions 上跑，由阿里云服务器的定时器每天 7:00 触发**。不用 GitHub 自己的定时，因为它延迟大、不稳定。

## 一、放在哪：阿里云还是 GitHub

2026-11-12 在阿里云那台服务器（深圳，`ssh wzry`）上实测了各渠道能不能访问。测试脚本是 `scripts/nettest.sh`，每个地址发一次请求，20 秒超时。

| 用途 | 地址 | 阿里云上的结果 |
|---|---|---|
| 采集 | Hacker News 接口 | 通，1.2 秒 |
| 采集 | three.js 论坛 | 通，4.5 秒 |
| 采集 | GitHub 搜索接口 | 通，0.7 秒 |
| 采集 | Spawn、Verse8、Astrocade、Rosebud、Wavedash | 都通，1 到 3 秒 |
| 采集 | itch.io 榜单 | **连不上** |
| 采集 | GitHub 原始文件（精选清单用） | **连不上**。已加了改走 GitHub 接口的备用路径 |
| X 帖子 | fxtwitter 接口 | 通，1.2 秒 |
| X 帖子 | t.co 短链展开 | **超时** |
| X 帖子 | x.com 原帖 | **连不上** |
| 游戏页面 | claude.ai、独立域名、pages.dev、netlify | 通 |
| 游戏页面 | github.io | 很慢，20 秒内没下完 |
| 游戏页面 | vercel.app、itch.io | **超时** |
| 推数据 | github.com | 很慢，20 秒超时 |

结论：阿里云访问不全。10 个固定渠道里 itch.io 采不了；X 帖子自带的短链展不开，这一步是 X 数据接入的基础；以后筛选时要打开的游戏页面有三类打不开或很慢。所以**采集放在 GitHub Actions 上**，服务器只负责定时触发（它能正常访问 GitHub 接口，0.7 秒）。GitHub 的机器在海外，这些地址按理都能访问，但还没有实际跑过，第一次运行后要看日志确认。

## 二、部署步骤

本机没有装 `gh`，建仓库、推送和生成令牌要你自己做。前 5 步在 GitHub 和本机，后 3 步在服务器。

1. 在 GitHub 网页新建一个仓库，例如 `webgame-monitor`，**不要**勾选"Add a README"。
   - 现在不出网页，不需要 GitHub Pages，所以选 **Private** 就行，数据不会公开。私有仓库的 Actions 免费额度是每月 2,000 分钟，这个任务每天约 5 分钟。
   - 选 Public 也能跑，但 `raw/` 下每天采到的线索和帖子原文任何人都能看到。
2. 在本机这个目录里执行（把地址换成你的）：
   ```bash
   git remote add origin git@github.com:<用户名>/webgame-monitor.git
   ```
   ```bash
   git push -u origin main
   ```
3. 仓库页面 → Settings → Actions → General → Workflow permissions 选 **Read and write permissions**。
4. 打开 Actions 页，选"每日采集"，点 **Run workflow** 手动跑一次。
5. 看这次运行的日志：最后一行应该是"各渠道都取到了数"；如果写着"出错的渠道：…"，把日志发给我。
6. 准备触发用的令牌，二选一：
   - 给 taptap 现在用的那个令牌加上这个新仓库（GitHub → Settings → Developer settings → Fine-grained tokens → 编辑 → Repository access 里勾上新仓库），然后在服务器上执行：
     ```bash
     sudo mkdir -p /etc/webgame-monitor && sudo cp /etc/taptap/github_token /etc/webgame-monitor/github_token && sudo chmod 600 /etc/webgame-monitor/github_token
     ```
   - 或者新建一个只给这个仓库用的令牌（权限 Actions: Read and write），按 `install_trigger.sh` 的提示写进 `/etc/webgame-monitor/github_token`。
7. 仓库名如果不是 `windsknow/webgame-monitor`，在服务器上把实际的名字写进去：
   ```bash
   sudo sh -c 'echo <用户名>/<仓库名> > /etc/webgame-monitor/repo'
   ```
8. 在本机把触发脚本传到服务器，再在服务器上安装定时器（安装时会先试触发一次）：
   ```bash
   bash deploy/aliyun/push_trigger.sh
   ```
   ```bash
   ssh wzry 'sudo bash /opt/webgame-monitor/deploy/install_trigger.sh'
   ```

之后服务器每天北京时间 7:00 触发一次（2026-11-13 从 10:30 改到 7:00），采到的数据会自动提交回仓库。

- 看触发记录：`ssh wzry 'journalctl -u webgame-trigger.service -n 20 --no-pager'`
- 手动补触发某一天：`ssh wzry 'sudo /opt/webgame-monitor/deploy/trigger_github.sh 2026-11-13'`
- 停用：`ssh wzry 'sudo bash /opt/webgame-monitor/deploy/uninstall_trigger.sh'`

要留意的一点：没有 GitHub 自己的定时做兜底，令牌过期或服务器停机时当天就不会采集。触发失败会记在上面的触发记录里。

**不会**进仓库的（已写进 `.gitignore`）：`inbox/x/`（对方送来的完整帖子数据）、`data/private/`（体验记录）。

### 把数据取回本机

```bash
git pull
```

每天的线索在 `raw/<渠道>/<日期>.json`，各渠道取到多少条在 `data/runlog.json`。

### X 数据的拉取地址（拿到之后）

Settings → Secrets and variables → Actions → New repository secret：

- `X_PULL_URL`：拉取地址，日期用 `{date}` 占位，例如 `https://example.com/x/{date}.json`
- `X_PULL_TOKEN`：如果需要鉴权才填。默认按 `Authorization: Bearer <令牌>` 发送，格式可以在 `config.json` 的 `x_pull.auth_header` 里改

如果这个地址只有公司内网能访问，GitHub 的机器拉不到，要等迁到内部平台后再接。

注意：对方送来的完整帖子文件只在运行时使用，不会提交进仓库；存下来的是粗筛命中的帖子（`raw/x/<日期>.json`）。如果想把完整文件也留着以后重新筛，需要另找地方存，这一点还没定。

## 三、采集存了什么

采集范围比入库线宽，目的是先把内容存下来（`config.json` 的 `thresholds.collect`）：

| 渠道 | 存下来的范围 |
|---|---|
| Hacker News | 近 7 天 ≥ 5 分、标题像在讲游戏的帖子，加上全部 Show HN |
| three.js 论坛 | 作品区周榜的全部帖子和首帖里的外链 |
| GitHub | 六个搜索词下近 30 天新建、≥ 5 星的仓库（每个词最多 50 个） |
| itch.io | 网页平台新品与热门榜的全部条目 |
| AI 游戏精选清单 | 和上次相比新增的条目 |
| Spawn、Verse8、Astrocade、Rosebud、Wavedash | 热门页的全部条目 |
| X 帖子 | 粗筛命中的帖子，带展开后的链接和规则判断 |

每条线索上的 `passes` 只是"按现在的入库线算不算过线"的标注，不影响存不存。

## 四、以后迁移

采集只依赖 Python 3（3.9 以上）标准库和 `curl`，入口只有一条命令 `python3 run.py crawl`，换地方跑不用改代码。迁移时：

1. **先测网络**：在新机器上跑 `scripts/nettest.sh`，对照上面的表看哪些地址不通。
2. **搬数据**：`raw/`、`data/state/`（各榜单上次的状态，丢了会把在榜的游戏都当成新上榜）、`data/runlog.json`。用 `git clone` 或直接拷贝都行。
3. **配定时**：每天一次，北京时间 7:00。需要的环境变量：`TZ=Asia/Shanghai`，可选 `X_PULL_URL`、`X_PULL_TOKEN`、`GITHUB_TOKEN`（有的话 GitHub 搜索的频率限制宽很多）。
4. **停掉旧的触发**：在服务器上跑 `uninstall_trigger.sh`，免得两边同时采。

### 把采集也搬到阿里云（文件已备好，没有安装）

`deploy/aliyun-direct/` 里按那台服务器的惯例（`/opt/<名字>`、独立系统用户、systemd 定时器）写好了直接在服务器上采集的版本：

```bash
bash deploy/aliyun-direct/push.sh
```

```bash
ssh wzry 'sudo bash /opt/webgame-monitor/deploy/aliyun-direct/install.sh'
```

取回数据用 `bash deploy/aliyun-direct/pull.sh`，停用用服务器上的 `deploy/aliyun-direct/uninstall.sh`。

迁过去之前要先解决上面表里不通的三项：itch.io、t.co 短链、游戏页面。可行的办法是给服务器配一个能访问这些地址的出口，或者这几项留在 GitHub 上跑。

### 迁到公司内部平台

| 要确认的 | 如果可以 | 如果不行 |
|---|---|---|
| 有没有定时任务（CI） | 把 `.github/workflows/daily.yml` 改写成对应平台的格式，命令不变 | 用服务器的定时器触发，和现在一样 |
| 定时任务的机器能不能访问外网 | 用 `scripts/nettest.sh` 测，都通就直接在内部跑 | 采集留在 GitHub Actions，内部平台定时拉取仓库的数据 |
| X 数据的拉取地址是不是内网地址 | 内部平台能直接拉 | 需要对方提供外网能访问的地址 |

## 五、筛选标准定下来之后

1. 把 `.github/workflows/daily.yml` 里的 `python3 run.py crawl` 换成 `python3 run.py daily`，提交步骤的 `git add raw data` 换成 `git add raw data assets digest`。
2. 要出网页时，把 `config.json` 的 `site.enabled` 改成 `true`，并在工作流里加回 Pages 的发布步骤（`actions/configure-pages`、`actions/upload-pages-artifact`、`actions/deploy-pages`，权限加 `pages: write` 和 `id-token: write`）。GitHub Pages 免费版要求仓库公开。
3. 汇总文本在 `digest/` 下，现在还没有接推送渠道。

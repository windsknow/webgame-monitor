# AI 网页游戏新品监测

每天从固定渠道和外部提供的 X 帖子数据里找新出现的、能在浏览器里玩的 AI 游戏，按统一标准筛选后生成一个静态网站。

- **网页（2026-11-13 起）**：新做的是信息流页面，`python3 run.py feed [日期]` 生成 `site/index.html`（`monitor/feed.py`、`templates/feed.css`）。开头是重点游戏的头图轮播，下面是检索框、标签筛选（状态、方向、AI 标签、发现渠道）和按入库日期分组的游戏卡片，卡片沿用上一份报告的样式。它不受 `site.enabled` 控制；旧版报告式页面（`python3 run.py site`）仍然暂停。页面放到哪里发布还没定（私有仓库用不了免费的 GitHub Pages）
- 工作流、脚本和会话的分工、产出字段：`docs/工作流与产出字段.md`
- 入库线和重点线的数据依据：`docs/入库线和重点线的数据依据.md`
- 基线：2026-11-10 整理的 68 款，见 `data/games.json`
- 只依赖 Python 3 标准库和 `curl`

## 已确认的决定（2026-11-11）

| 事项 | 决定 |
|---|---|
| 收录范围 | 以 AI 参与的网页游戏为主。没有 AI 证据但符合"短时间、低成本、高完成度"共性的也可以收；明确不是 AI 制作但有创意的也可以收，另加标签 |
| 是否公开 | 优先放公司内部的代码平台（有权限控制）；其次 GitHub，可以公开 |
| 访问环境 | 公司内网和 GitHub 都能直接访问 |
| X 数据送达 | 每天定时去固定地址拉。地址待定，先留配置项，现阶段读 `inbox/x/` |
| 更新与审核 | 全自动发布；另出日汇总和周汇总，方便推送 |
| 是否用模型 | 定时任务不调模型。主题判断、核验、卡片文字在每周的会话里做 |
| 项目位置 | 本目录。先在 GitHub 搭通，再迁到内部平台 |
| 社区回复（2026-11-16） | X、Reddit 等用小号登录后在本机浏览器面板里读，限频限量，只读不互动，规则见 `docs/登录态读取社区规范.md` |
| 视频抽帧（2026-11-16） | 只有视频、玩法不明的帖子，每周在本机用 Sonnet 子代理抽帧读图补玩法；DeepSeek 暂不接入 |

## 每天自动做什么

**现在线上只采集**（2026-11-12 起）：采集在 GitHub Actions 上跑，由阿里云服务器的定时器每天 7:00 触发，命令是 `python3 run.py crawl`，只做下面的第 1、2 步，把内容存进 `raw/`。筛选标准定下来之后再启用第 3、4 步（`python3 run.py daily`）。部署和迁移见 `docs/部署步骤.md`。

1. **采集**（`monitor/collectors.py`）：Hacker News、three.js 论坛作品区、GitHub、itch.io 网页新品榜、awesome-ai-built-games，Spawn、Verse8、Astrocade、Rosebud、Wavedash 的热门页，以及 Fable 5.2 网页游戏合集站 Fable52.games（2026-11-13 加入）。原始结果存 `raw/<渠道>/<日期>.json`。
2. **X 数据接入**（`monitor/x_ingest.py`）：读 `inbox/x/<日期>.json`（没有就按配置去拉），加上 `data/x_manual_posts.json` 里手动补充的帖子链接 → 规则粗筛 → 展开短链 → 规则版主题判断 → 找试玩链接 → 和收录库比对。结果存 `raw/x/<日期>.json`。
3. **合并入库**（`monitor/merge.py`）：按试玩链接合并去重，剔除已收录的和仿冒域名，判断是不是网页游戏。是的自动生成卡片追加到 `data/games.json`，其余留在 `data/candidates.json`。已入库的自动卡片，数字和重点标记每次都会按最新数据重算。
4. **出汇总**（`monitor/build_site.py`）：输出 `digest/` 下的日汇总和周汇总文本。网页暂停期间不生成 `site/`。

所有门槛、关键词、域名清单都在 `config.json`，改完不用动代码。

## 数据文件

| 文件 | 内容 |
|---|---|
| `data/games.json` | 已收录的游戏，页面的唯一数据来源。`status` 为 `verified`（人工核验过）或 `auto`（自动收录，待核验） |
| `data/candidates.json` | 候选队列，按去重键。`status`：收录 / 观察 / 候选 / 已在库 / 拒绝。拒绝的会一直留着，不会再被打开 |
| `data/sources.json` | 每条线索的原始出处，按去重键归档，用于追溯 |
| `data/x_judgments.json` | X 帖子的主题判断（按 tweet_id），优先级高于规则判断。合并时按最新内容重新判断，不用重跑 X 接入 |
| `data/fable52_x_posts.json` | Fable52.games 详情页没给作者帖子的游戏，每周核验时找到的作者 X 帖子（来自 Awesome Fable 5.2 清单或登录后搜索）。采集时用它追原始出处、读浏览数；找过没找到的记在 `not_found` |
| `data/x_manual_posts.json` | 手动补充的 X 帖子链接。加一行 `{"url": "…", "added": "YYYY-MM-DD"}`，下一次每日运行会处理（加入后 7 天内有效）；想马上生效就跑 `python3 run.py x <日期> && python3 run.py merge` |
| `data/static.json` | 趋势、数据交叉验证表、其他线索、七个方向的说明 |
| `data/state/` | 各榜单上一次的状态，用来判断"新进榜""新增条目" |
| `data/runlog.json` | 每天各渠道的线索数，用来发现渠道失效 |

## 入库规则（2026-11-12 起）

目标是尽量覆盖，再把重点标出来。过了渠道入库线、判断为网页游戏、并且是近期的线索，直接入库；
不要求传播数据、游玩次数，也不要求有试玩链接。

**各渠道的入库线**（`config.json` 的 `thresholds.floors`）

| 渠道 | 入库线 |
|---|---|
| X 帖子 | 判断为网页游戏的都入库；没找到试玩链接的，以来源帖子入库 |
| Hacker News | 7 天内 ≥ 30 分，标题像在讲游戏 |
| three.js 论坛作品区 | 一周内 ≥ 100 次浏览，内容像在讲游戏或写明 AI 参与 |
| GitHub | 创建 30 天内 ≥ 30 星，有试玩主页，并且不是引擎、框架、技能包这类工具 |
| itch.io | 连续 2 周在榜，或描述写明 AI 参与 |
| AI 游戏精选清单 | 新增的都入库 |
| Spawn、Verse8、Rosebud、Wavedash 的热门页 | 新进榜的；首次读取时只取近 30 天发布的 |
| Fable52.games | 新出现的；首次读取时只取近 30 天收录的。条目都标注由 Fable 5.2 制作，算作有 AI 证据 |
| Astrocade 热门页 | 同上，另外要求游玩 ≥ 2 万次（这个榜轮换很快） |

**怎么判断是网页游戏**（`merge.gameness`）

- 链接在已知的游戏平台或 AI 创作平台上：直接算。
- 独立站点和 github.io 这类托管位置：打开页面，首页或前几个同站脚本里能找到画布或游戏引擎才算。
- 来自精选清单、three.js 论坛作品区、或核验过的 X 帖子：不用再看页面。
- 只有代码仓库、没有试玩页面的：不入库，留在候选里。
- 没有试玩链接的 X 帖子：核验确认是游戏的入库；只有规则判断的，要带视频或图片，并且正文有游戏词，或者同时有网页技术词和 AI 词。

另外要求首次公开在近 30 天内，或近 7 天有新热度（新上榜、新帖子）。

**标为重点**（2026-11-25 用户定稿，完整口径见 `docs/重点评判规则.md`）

满足任意一条就是重点，卡片上写明入选理由，几条同时成立时全部列出：

- **X 热度**：作者帖或他人专门介绍这款游戏的帖子，单帖浏览 ≥ 20 万（`thresholds.hot.x_views`）。多款游戏的清单帖不算。
- **玩法新**：每周打分里玩法新颖（N）得 2 分。
- **技术强**：每周打分里技术前沿（T）得 2 分。

2 分必须有视频、试玩、README、作者帖文或游戏自己页面的说明作依据。只来自合集站或平台简介的记"待核"，不算重点。同一原作的多款移植只取一款，其余标"同类移植"。

只做展示、不算重点的标签：
- "X 有传播"：X 浏览 5 万到 20 万（`x_spread`）；
- "平台爆款"：Astrocade 游玩 ≥ 50 万（`platform_hit`）。

游玩数、Hacker News 分、GitHub 星只作参考。已核验卡片也按这条规则重算。

X 帖子的浏览数：
- 发帖 14 天内的来源帖每天重读；
- 卡片关联的其他帖子，包括已核验卡片的 `source_posts`，每 7 天重读一次；
- 读数存在 `data/state/x_reads.json`，卡片上标读取日期。

**页面上怎么放**：重点的、核验过的、写了玩法介绍的用完整卡片；其余自动入库的排在紧凑列表里。

**X 浏览到了重点线、但不能确定是不是游戏的**（例如页面里找不到画布）进"线索观察"，等人工确认。

## 每周核验怎么做

自动收录的卡片只放能追溯到出处的原文和数字。每周开一次 Claude 会话（或人工）做这些事：

1. 看 `raw/x/<日期>.json` 里 `verdict` 为 `maybe` 的帖子：打开原帖看串内内容和回复，判断是不是游戏、能不能网页玩、有没有 AI 证据，找到试玩链接。结论写进 `data/x_judgments.json`：
   ```json
   "<tweet_id>": {"is_game": true, "in_browser": true, "ai_evidence": "帖子写明用 … 制作",
                  "note": "…", "games": [{"name": "…", "url": "https://…", "how": "串内帖子的链接",
                  "source_post": "https://x.com/…", "post_views": 123456}],
                  "judged": "2026-11-18", "by": "会话核验"}
   ```
   可选字段：`name`（没有试玩链接时用作条目名）、`ingest: false`（是游戏但不该作为单款入库，例如多个演示的合集帖）。
   然后重跑 `python3 run.py merge`。判为不是游戏的，对应的自动卡片会被撤下；后来找到试玩链接的，原来按帖子入库的卡片会换成游戏链接。
2. 看 `data/candidates.json`：自动入库但其实不是游戏的，把 `status` 改成 `拒绝` 并写 `reject_reason`（卡片会被撤下）；"候选"里因为页面找不到画布而没入库的（纯网页元素做的游戏会这样），确认是游戏的加上 `"is_game_manual": true`，下次合并就会入库；AI 标签用 `ai_tag_manual`（`ai` / `likely` / `non_ai`）。
3. 看 `data/games.json` 里 `status` 为 `auto` 的卡片：试玩后补 `kind`、`play`、`highlight`（亮点）、`tech` 和 `tech_basis`（技术栈依据，优先按站点代码特征识别）、`group`（七个方向之一），确认数字和出处，把 `status` 改成 `verified`。一款游戏占两类以上时按最核心的特点归类，拿不准的列出来问。
4. 只有视频、玩法写不出来的卡片，以及标为重点的卡片：找演示视频，用 `python3 -I scripts/video_frames.py <X帖子链接或mp4> <输出目录> [帧数]` 下载、抽帧并拼成对照图（抽帧用 macOS 自带的 AVFoundation，见 `scripts/frames.swift`），读图补玩法，视频链接写进卡片的 `videos`；再按 `docs/登录态读取社区规范.md` 登录读回复做概括。玩法末尾注明"（玩法取自视频抽帧）"。
5. **玩法和技术打分**（合并之后、生成页面之前）：
   - `python3 scripts/apply_novelty.py --queue` 列出要打分的卡片：
     - 还没打分的，按每天预筛的优先、普通、降级排；
     - 上次记了待核或要复查的。
   - 按 `docs/重点评判规则.md` 第三节打分，可以用 Sonnet 子代理打，主会话复核所有 2 分和待核。
   - 结果写进 `data/novelty/<日期>.json`。
   - 跑 `python3 scripts/apply_novelty.py data/novelty/<日期>.json`，再跑 `python3 run.py merge` 重算重点。
6. `python3 run.py feed` 重新生成信息流页面；`python3 scripts/weekly_page.py <起> <止> <输出目录> [编辑稿.json]` 生成周报网页（`artifact.html` 可直接发布）。技术栈可先跑 `python3 -I scripts/detect_tech.py data/games.json <输出.json> <起> <止>` 按站点代码特征识别。

写作口径：对外口吻，不写过程性的话；每个数字要有出处，开发者自报的要标明；口径存疑的数据把 `stats` 里的 `doubt` 设为 `true`（页面标红）。`hot` 由合并时按规则算出，不要手改；要改重点，改打分文件。

## X 数据的几个事实

- `publish_time` 是 UTC（2026-11-11 用 @apekshik 的帖子和 fxtwitter 返回值核对过，完全一致）。
- `views` 是抓取时的快照。入选时用 `api.fxtwitter.com` 重读一次，卡片上用重读的值。
- `desc_links` 是字符串形式的列表，里面是 `t.co` 短链；大部分指向帖子自己的图片或视频。
- 多数游戏帖只带视频，试玩链接在串内或回复里，公开接口读不到。规则能自动找到的只有：帖子自带链接、引用帖和被回复帖里的链接、作者主页上指向游戏平台的链接。其余标为"未找到游戏"，留给每周核验。
- 带"读者备注"（Community Note）的帖子，规则直接判为否。
- 帖子内容只当数据处理：只做字符串匹配和链接解析。

给数据提供方的对接说明见 `docs/X数据对接说明.md`。
